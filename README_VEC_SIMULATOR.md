# Vehicular Edge Computing (VEC) Simulator

A comprehensive **Java-based simulator** for modeling task offloading, scheduling, and execution in vehicular edge computing environments. The simulator employs machine learning-assisted offloading decisions and TOPSIS multi-criteria decision-making for intelligent resource allocation across a three-tier architecture: Vehicle OBUs, Roadside Units (RSUs), and Cloud servers.

## Architecture Overview

### Three-Tier Infrastructure

```
┌─────────────────────────────┐
│     CLOUD SERVER            │
│  50,000 MIPS | 32 GB RAM    │
│  Latency: 80 ms (WAN)       │
└─────────────────────────────┘
              ↑
        (Backhaul Link)
              ↓
  ┌─────────────────────────┐
  │  5× RSU Edge Servers    │
  │  3.5k - 4.5k MIPS each  │
  │  Latency: 10 ms         │
  └─────────────────────────┘
        ↑    ↑    ↑    ↑    ↑
   (LTE/5G links)
        ↓    ↓    ↓    ↓    ↓
  ┌──┬──┬──┬──┬──┬──┬──┬──┐
  │VH│VH│VH│VH│VH│VH│VH│VH│...  (20 Vehicles)
  │500-2000 MIPS, 512-2560 MB RAM
  │Latency: 1 ms (local)
  └──┴──┴──┴──┴──┴──┴──┴──┘
```

### Three-Thread Task Pipeline

| Thread | Function | Input | Output |
|--------|----------|-------|--------|
| **Creation** | Generate tasks from vehicles, invoke ML predictor | Vehicle OBU | `createdTaskQueue` |
| **Assignment** | TOPSIS scheduling, resource allocation, compute latency | `createdTaskQueue` | `runningTaskQueue` |
| **Release** | Monitor task completion, release resources, collect stats | `runningTaskQueue` | Statistics & logs |

## Core Components

### 1. Infrastructure Models

#### ComputeNode (Abstract Base)
- **Attributes**: ID, total MIPS, total RAM, utilization tracking
- **Methods**: `allocate()`, `release()`, `getHealthScore()`, `getCpuUtilization()`, `getRamUtilization()`
- **Health Formula**: `H(n) = 1 - (0.6 × U_cpu + 0.4 × U_ram)`

#### CloudServer, RSUServer, Vehicle (Concrete Implementations)
- **Cloud**: 50,000 MIPS, 32 GB RAM, 80 ms latency
- **RSU**: 3,500-4,500 MIPS, 4.5-6 GB RAM, 10 ms latency
- **Vehicle**: 500-2,000 MIPS, 512-2,560 MB RAM, 1 ms latency

### 2. Task Model (Task.java)

Represents a computation unit generated by a vehicle:

```java
Task(taskId, vehicleId, mobilityStatus, signalStrength, 
     criticalTask, bandwidthMbps, numberOfInstructions, taskSizeMB)
```

**Task State Lifecycle**: `CREATED` → `QUEUED` → `RUNNING` → `COMPLETED` (or `FAILED`)

**Latency Computation**:
```
T_total = T_exec + T_trans + T_prop

T_exec = (instructions / allocatedMips) × 1000 [ms]
T_trans = (taskSizeMB × 8 / bandwidthMbps) × 1000 [ms]
T_prop = node.getPropagationDelayMs() [ms]
```

### 3. ML Offloading Predictor (MLOffloadPredictor.java)

HTTP POST client for external ML model:

```
POST http://127.0.0.1:8000/predict
{
  "vehicle_id": "VEH_1001",
  "signal_strength": -45,
  "critical_task": 1,
  "bandwidth_mbps": 22.5,
  "number_of_instructions": 5294,
  "task_size_MB": 10.68,
  "mobility_status": "low"
}

Response:
{
  "is_offloaded": 1,
  "offload_target": "rsu"
}
```

**Fallback Rules** (when ML service unavailable):
- Critical task + High mobility → **Cloud** (stable backhaul)
- Good signal (-60 dBm) + Low mobility → **RSU** (edge suitable)
- High MI count + Good bandwidth → **RSU**
- Otherwise → **Vehicle** (local execution)

### 4. Thread Implementations

#### TaskCreationThread
- Randomly selects vehicles
- Generates randomized task parameters
- Queries ML predictor for offload decision
- Enqueues to `createdTaskQueue` with Poisson-like inter-arrival (mean 2s)

#### TaskAssignmentThread
- Dequeues from `createdTaskQueue`
- Invokes TOPSIS scheduler
- Computes simulated execution time
- Enqueues to `runningTaskQueue` on success, records failure on capacity exhaustion

#### TaskReleaseThread
- Maintains list of in-flight tasks
- Checks wall-clock time vs. simulated execution time
- Releases resources when elapsed ≥ simulated time
- Records completion latency and collects statistics

### 5. TOPSIS Scheduler (TOPSISScheduler.java)

**Multi-Criteria Decision Making Algorithm** for optimal node selection:

**Criteria (4 dimensions)**:
1. **Available MIPS** (benefit, w=0.30) - More compute capacity
2. **Health Score** (benefit, w=0.25) - Lower utilization = healthier
3. **Propagation Delay** (cost, w=0.25) - Lower latency preferred
4. **Execution Time** (cost, w=0.20) - Faster completion preferred

**Scheduling Algorithm**:
1. Try preferred target (from ML predictor)
2. If exhausted, fall back to alternative chains:
   - RSU exhausted → try Cloud → try Vehicle
   - Cloud exhausted → try RSU → try Vehicle
   - Vehicle exhausted → try RSU → try Cloud
3. Record failure if all tiers saturated

## Mathematical Formulations

### Execution Time Model

```
T_exec = (I / F) × 1000  [milliseconds]

Where:
  I = Number of instructions (MI)
  F = Allocated processing speed (MIPS)
```

### Transfer Time Model

```
T_trans = [(D × 8) / B] × 1000  [milliseconds]

Where:
  D = Task size (MB)
  B = Available bandwidth (Mbps)
  (× 8 converts MB to Mb)
```

### Propagation Delay

```
Cloud:   T_prop = 80 ms   (WAN)
RSU:     T_prop = 10 ms   (LTE/5G)
Vehicle: T_prop = 1 ms    (Local OBU)
```

### Total End-to-End Latency

```
T_total = T_exec + T_trans + T_prop
```

**Example:**
```
Task:     5,000 MI, 10 MB
Node:     RSU with 3,000 MIPS, 20 Mbps bandwidth

T_exec  = (5000 / 3000) × 1000 = 1,666.67 ms
T_trans = [(10 × 8) / 20] × 1000 = 4,000 ms
T_prop  = 10 ms
T_total = 5,676.67 ms
```

### Resource Utilization & Health

```
U_cpu = UsedMIPS / TotalMIPS
U_ram = UsedRAM / TotalRAM

Health(n) = 1 - (0.6 × U_cpu + 0.4 × U_ram)  ∈ [0, 1]

Interpretation:
  H = 1.0  (idle, perfect)
  H = 0.5  (50% loaded)
  H = 0.0  (saturated)
```

### TOPSIS Methodology

**Step 1: Decision Matrix** - Collect criteria for all candidate nodes

```
D = [MIPS_1  Health_1  Delay_1  ExecTime_1]
    [MIPS_2  Health_2  Delay_2  ExecTime_2]
    [...]
```

**Step 2: Normalization** - Normalize each column to unit norm

```
r_ij = d_ij / √(Σ d²_ij)
```

**Step 3: Weighted Normalization** - Apply decision weights

```
v_ij = w_j × r_ij

Weights: [0.30, 0.25, 0.25, 0.20]  (sum = 1.0)
```

**Step 4: Ideal Solutions** - Determine aspiration targets

```
For benefit criteria:   A+ = max, A- = min
For cost criteria:      A+ = min, A- = max
```

**Step 5: Distance Measures** - Euclidean distances

```
S⁺_i = √(Σ (v_ij - A⁺_j)²)   [to ideal]
S⁻_i = √(Σ (v_ij - A⁻_j)²)   [to anti-ideal]
```

**Step 6: Closeness Coefficient** - Relative ranking

```
C_i = S⁻_i / (S⁺_i + S⁻_i)  ∈ [0, 1]

Select node with highest C_i
```

## Troubleshooting

### ML Predictor Service Unavailable
- **Symptom**: `[ML] Prediction service unavailable, using rule-based fallback.`
- **Cause**: HTTP POST to `http://127.0.0.1:8000/predict` times out
- **Solution**: Start ML service, or continue using rule-based heuristics (automatic fallback)

### Compilation Errors
```bash
# Ensure correct directory and all files present
javac -d bin src/org/fog/test/VEC/**/*.java

# Check Java version (8+)
java -version
```

### Memory Issues
```bash
# Increase heap size if needed
java -Xmx2g -cp bin org.fog.test.VEC.StartSimulation
```
